# Hack The Box - Paper

> **Machine:** Paper  
> **Difficulty:** Easy  
> **OS:** Linux  
> **Target IP:** `10.129.136.31`

## Introduction

Paper is an Easy Linux machine from Hack The Box.

The machine initially exposes SSH and HTTP/HTTPS services. Enumeration leads to a WordPress installation hosted on the `office.paper` virtual host. A static WordPress page reveals an internal Rocket.Chat instance.

After registering an account on Rocket.Chat, I discovered a bot named `recyclops`. The bot was vulnerable to path traversal, which allowed access to files outside its intended directory. This eventually exposed the Hubot `.env` file containing credentials.

The credentials could be reused to obtain SSH access as `dwight`.

Further analysis of the Hubot source code revealed an extremely dangerous command execution functionality using Node.js `child_process.exec()`. This provided command execution as Dwight.

For privilege escalation, system enumeration revealed CentOS 8 running Polkit 0.115 with AccountsService installed. These conditions led to **CVE-2021-3560**, a Polkit race-condition vulnerability that could be used to create a privileged user.

The newly created user was added to the `wheel` group, which was allowed unrestricted sudo access through `/etc/sudoers`.

8. SSH Access as Dwight

The password worked for the dwight account over SSH.

One small issue I encountered was the ! character in the password.

When passing passwords through Bash, characters such as ! can have special meaning depending on the shell configuration.

Using single quotes prevented Bash from interpreting the character:

sshpass -p 'Queenofblad3s!23' ssh dwight@10.129.136.31

This successfully authenticated as:

dwight

At this point I had a stable SSH foothold.

10. Command Execution in run.js

The most interesting discovery was run.js.

The source code contained:

module.exports = function(robot) {
    robot.respond("/RUN (.*)$/i", function(msg) {
        console.log(msg);

        var cmd = msg.match[1];

        msg.send("Running " + cmd);

        var exec = require('child_process').exec;

        exec(cmd, function(error, stdout, stderr) {
            if (error) {
                msg.send(error);
                msg.send(stderr);
            } else {
                msg.send(stdout);
            }
        });
    });
};

This was effectively an arbitrary command execution vulnerability.

The flow was:

User input
    │
    ▼
msg.match[1]
    │
    ▼
cmd
    │
    ▼
child_process.exec()
    │
    ▼
Operating system command

The application was taking attacker-controlled input and directly passing it to:

child_process.exec()

without any meaningful restriction.

This is a classic example of OS command injection / arbitrary command execution.

16. CVE-2021-3560 Overview

CVE-2021-3560 is a privilege escalation vulnerability involving Polkit and AccountsService.

Polkit is responsible for authorization decisions for various privileged operations.

AccountsService provides functionality for managing user accounts.

Normally, an unprivileged user should not be able to perform privileged account-management operations.

The vulnerability involves a race condition in the authorization process.

Conceptually:

               Dwight
                  │
                  ▼
           AccountsService
                  │
                  ▼
                Polkit
                  │
          Authorization check
                  │
             RACE CONDITION
                  │
                  ▼
        Privileged operation
                  │
                  ▼
           Create account

The exploit attempts to win this race.

Because the attack depends on timing, multiple attempts may be necessary.

The POC itself warns:

Usually multiple attempts are required to get the timing right.

This turned out to be important during exploitation.

18. Investigating the Failed Privilege Escalation

Once inside the secnigma shell, I checked my identity:

The result was:

uid=1005 gid=1005 groups=1005,10(wheel)

At first this looked promising.

The new user was apparently a member of wheel.

However, when I ran:

whoami

whoami: cannot find name for user ID 1005

This was unusual.

I checked /etc/passwd:

The end of the file contained:

This demonstrated an important Linux concept.

The shell had numeric credentials:

UID 1005

but the system could not resolve UID 1005 to a normal user entry.

This explained:

19. Why sudo bash Failed

I attempted:

sudo bash

but received:

sudo: you do not exist in the passwd database

At first this seemed strange because:

groups=1005,10(wheel)

showed membership in wheel.

The problem was that the account created during this exploit attempt was incomplete.

The process had the expected UID/group credentials, but the normal account database did not contain the corresponding user.

Therefore sudo could not properly resolve the invoking identity.

This was an important lesson:

A privilege escalation exploit can partially succeed without leaving the system in the exact state expected by the post-exploitation step.

Because CVE-2021-3560 is a race condition, I reran the exploit.

21. Understanding wheel

After obtaining root, I inspected /etc/sudoers.

The relevant section was:

## Allows people in group wheel to run all commands
%wheel ALL=(ALL) ALL

This is what made the wheel membership useful.

Breaking it down:

%wheel

means the rule applies to the wheel group.

ALL

means it applies to all hosts.

(ALL)

means members can execute commands as any user.

ALL

means they can execute any command.

Therefore:

%wheel ALL=(ALL) ALL

effectively gives members of the wheel group unrestricted sudo access.

The exploit created secnigma with:

groups=1005,10(wheel)

The complete privilege escalation was therefore:

CVE-2021-3560
        │
        ▼
 Privileged account creation
        │
        ▼
  secnigma + wheel
        │
        ▼
%wheel ALL=(ALL) ALL
        │
        ▼
      sudo
        │
        ▼
       root
22. Why sudo bash Works

The command:

sudo bash

does not have anything specifically special about bash.

sudo is being used to execute the Bash program with elevated privileges.

Because no target user was explicitly specified, sudo defaults to root.

Conceptually:

sudo bash
   │
   ▼
sudo authorization
   │
   ▼
wheel membership
   │
   ▼
execute /bin/bash as root
   │
   ▼
UID 0

The result:

uid=0(root) gid=0(root) groups=0(root)

confirmed successful privilege escalation.

25. Lessons Learned
25.1 Enumeration should lead to hypotheses

One of the biggest lessons from Paper was learning how to move from enumeration to exploit selection.

Instead of:

LinPEAS → CVE → run exploit

a better methodology is:

OS
 ↓
Software
 ↓
Version
 ↓
Configuration
 ↓
Known vulnerabilities
 ↓
Prerequisites
 ↓
Exploit

For Paper:

CentOS 8
    ↓
Polkit
    ↓
Polkit 0.115
    ↓
AccountsService installed
    ↓
CVE-2021-3560 candidate
    ↓
Validate prerequisites
    ↓
Exploit
25.2 Don't blindly trust automated enumeration

LinPEAS produced a huge amount of information.

It is useful for identifying potential attack surfaces, but every finding still needs manual validation.

For example, simply seeing:

CVE-2019-13272

does not mean the machine is automatically exploitable.

The correct question is:

Does the machine satisfy the prerequisites of this vulnerability?

25.3 Version numbers matter

The installed package was:

polkit-0.115-6.el8.x86_64

The upstream Polkit version was:

0.115

while:

-6.el8

represents the CentOS package release.

This distinction is important when researching vulnerabilities.

25.4 Race conditions can produce inconsistent results

The first CVE-2021-3560 exploitation attempt produced a partially functional account.

The process had:

UID 1005

and:

wheel

but the account could not be resolved through /etc/passwd.

The second attempt produced a usable account.

This demonstrated why race-condition exploits may require multiple attempts.

A failed attempt does not necessarily mean:

"The machine is not vulnerable."

It may mean:

"The race was not won correctly."

25.5 Linux users are represented by numeric UIDs

The first secnigma attempt was a good demonstration of the difference between a process's numeric credentials and the system's user database.

The process had:

UID 1005

but:

getent passwd secnigma

returned nothing.

Therefore:

id

could still display:

uid=1005

while:

whoami

could not resolve the username.

25.6 Groups do not automatically mean root

Being a member of:

wheel

does not itself make a user root.

The important relationship was the sudoers configuration:

%wheel ALL=(ALL) ALL

Therefore the complete chain was:

secnigma
    ↓
wheel membership
    ↓
sudoers authorization
    ↓
sudo
    ↓
root
25.7 Source-code review can reveal vulnerabilities

The Hubot source code made the command execution vulnerability obvious.

The application essentially performed:

var cmd = msg.match[1];
exec(cmd, ...);

This meant attacker-controlled input reached an operating-system command execution function.

Similarly, files.js attempted to protect against command injection through a blacklist but failed to account for path traversal using:

..

This demonstrates why blacklists are generally poor security controls.

25.8 Credential reuse matters

The .env file contained:

ROCKETCHAT_PASSWORD=Queenofblad3s!23

The password was then useful for another account:

dwight

This demonstrates a common real-world attack path:

Application secret
      ↓
Credential reuse
      ↓
Different account/service
      ↓
Initial access
25.9 Failed exploitation is still valuable information

The first CVE attempt initially appeared to fail.

However, investigating the resulting state revealed:

UID 1005
wheel membership
missing passwd entry
sudo failure

Those observations helped explain exactly what had happened.

A failed exploit should not always be treated as wasted effort.

The error message can provide information about:

permissions
account state
execution context
missing prerequisites
race-condition timing
configuration
